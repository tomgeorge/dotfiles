Background

Our Pi extensions each claim their own ctrl+shift chord to open a panel. That doesn't scale, and nobody can see what's bound. DoomPi solves the same problem with a Doom Emacs–style leader key and a which-key map. This RFD compares DoomPi's editor with our vi-mode extension and proposes how to bring the leader into our setup.

Today three extensions register panel shortcuts directly with pi.registerShortcut:

ChordExtensionOpens
ctrl+shift+ccrew/index.tsCrew panel
ctrl+shift+ssubagent/index.tsSubagent jobs panel
ctrl+shift+wwatch/index.tsWatches and loops panel

Every new extension needs a new chord, chords collide with terminal and multiplexer bindings, and none of them can be discovered from inside Pi. The IDEAS.md entry proposes copying DoomPi's leader: SPC on an empty prompt opens a map of commands, keys narrow it step by step, and extensions contribute bindings to one registry.

The catch is that Pi has exactly one editor slot. ctx.ui.setEditorComponent replaces the prompt editor wholesale, and vi-mode already uses it. DoomPi's leader is its editor (DoomEditor). Both can't be installed at once, so we have to decide where the leader lives.

Scope

This compares DoomPi at commit c3f057a (2026-10-14, @agimon-ai/doompi-ui 0.0.1-alpha.128, MIT) with pi/extensions/vi-mode as it stands in this repository, running on Pi 1.0.2.

Three meanings of "mode"

"Modal editing" covers three different things in these codebases. Keeping them apart avoids most of the confusion.

Finding

DoomPi has no vi-style modal editing. A search of the repository for vim, normal mode, insert mode and modal finds only dialog modals and a persona prompt. Its prompt editor is Pi's default editor plus a leader. Its "modes" are the Emacs kind.

So the comparison isn't "DoomPi's vi mode against ours". It's DoomPi's leader and which-key against our vi editing, and how the two would share one editor.

The editors overlap very little. DoomEditor adds an entry point and a dispatcher. ViEditor rewires the meaning of almost every printable key. Combining them is mostly a question of who gets SPC first.

DoomPi's leader registry

The registry is the part worth copying. It's a tree of one-character keys built from flat contributions, with careful handling of conflicts. Here is the contract, from doompi-core/src/schemas/leader.ts:

type LeaderSegment = {
  key: string;          // one char, must match /^[a-z0-9]$/
  label: string;        // ≤ 32 chars
  detail?: string;      // ≤ 80 chars, the grey second line
  order?: number;       // group identity only; options sort by key
  tone?: "default" | "exit";  // "exit" paints the badge yellow
};

type LeaderBinding = { id: string; path: [LeaderSegment, ...LeaderSegment[]] }  // 1–4 segments
  & ({ command: { name: string; args?: string } }   // submits "/name args"
   | { action: { name: string } });                  // calls a handler the source registered

type LeaderContribution = { source: string; bindings: LeaderBinding[] };

Behaviour worth keeping

  • Parse at the boundary. register(value: unknown) validates every field: lengths, control characters, key and identifier patterns, duplicate ids, exactly one of command or action. A malformed contribution is rejected whole, with diagnostics. An unknown tone is ignored rather than rejected, so a package built against a newer contract doesn't lose its whole menu over a colour.
  • Last registration wins. When two sources claim the same leaf, the later one takes it and the registry reports who lost what (SPC c l taken over from crew). The tree is rebuilt from every stored contribution, so when the winner unregisters, the displaced binding comes back.
  • Re-registering is reclaiming. A source that registers again moves to the back of the order. A /reload therefore counts as a fresh claim.
  • Group labels may disagree. If two packages spell the SPC e group differently, the first label stays and a warning is logged, but both bindings work. Losing a key is worse than an inconsistent label.
  • Sort by key, not by order. A reader looking for a chord knows the key. order numbers scattered across many packages produce a sequence nobody can see.
  • Bindings can change at runtime. handle.update(bindings) swaps a source's bindings. Plan and goal use this to show e enter when off and e exit (yellow, tone: "exit") when on.
  • Commands are checked before they run. The editor asks pi.getCommands() whether /name exists and warns instead of submitting an unknown command. It also keeps the draft: it clears the text, submits the command, then restores the draft.

The which-key panel

The editor publishes a LeaderSnapshot (prefix, label, options, root options) on every step. A listener mounts LeaderHints as a widget with placement: "belowEditor", and removes it when the leader closes. The panel shows up the moment SPC is pressed; unlike Emacs which-key, there's no idle delay.

  • Fixed grid. The column count depends only on terminal width (4 columns from 130 wide, 3 from 90, 2 from 56, otherwise 1), so every board lines up the same way. Cells are equal width and long details are cut with an ellipsis.
  • Two-line cards. Key badge and bold label, then the grey detail underneath. If there isn't room, details are dropped before options are.
  • Hard height cap. 21 rows, including padding. Options get space before diagnostics, because a truncated option is a key you can't see.
  • Shade, not frame. A background tint sets the panel apart, saving the two rows a border would take.
  • Root board extras. MODES, SESSION and EXTENSIONS rows summarise the session. On wide terminals, a root trail of top-level keys stays visible on sub-boards.

We'd want the grid, the cards, the cap and the breadcrumb. We'd skip the diagnostics rows: the footer and the crew, subagent and watch widgets already show that information.

Where the leader lives

Pi allows one editor component, so the leader has to live in whichever editor is installed. These are the options.

A. A LEADER mode inside vi-mode proposed

Add a third, transient mode to ViEditor. The tree walk goes in a pure leader.ts beside engine.ts, and the registry in leaderRegistry.ts. One editor owns all key routing, so the SPC and Esc rules can be designed together. Cost: vi-mode stops being only about vi.

B. A shared "editor" extension that composes layers later

One extension owns setEditorComponent and stacks key handlers (leader, vi) that each return handled or pass. It's the cleanest separation, but it's a framework for two users. Worth doing only if a third key layer shows up. Option A's pure modules make that split easy later.

C. Install @agimon-ai/doompi-ui alongside rejected

Whichever setEditorComponent call runs last wins, so we'd lose vi-mode or the leader. Its hub is also a Cordis service, and the whole DoomPi host is bundled into one runtime. We'd be taking a distribution to get one feature.

D. A separate leader extension that doesn't own the editor rejected

Open the which-key map from a registerShortcut chord into a ctx.ui.custom overlay. This needs no editor changes, but it loses the SPC trigger, which is the point of the idea, and adds one more chord.

Proposed design

The leader becomes a transient third mode. It remembers which mode it came from and goes back to it when it closes.

Shape of the code

This follows vi-mode's existing split: pure modules decide, the editor applies.

// leader.ts: pure. Given the tree, the path so far and a key, say what happens.
export type LeaderStep =
  | { type: "descend"; path: string[] }       // re-render the panel
  | { type: "run"; target: Target }          // close, then dispatch
  | { type: "close" };                        // Esc, unknown key, BS at root

export function leaderKey(tree: Tree, path: string[], key: LeaderKey): LeaderStep;

// editor.ts: one more branch in handleInput, ahead of the paste guard.
if (this.leader) return this.leaderInput(data);
if (this.opensLeader(data)) return this.openLeader();   // remembers this.mode
if (this.mode === "insert") this.insertKey(data); else this.normalKey(data);

SPC in NORMAL mode

IDEAS.md asks whether SPC should be the leader in NORMAL too, and whether that clashes with a vi binding.

It doesn't clash. In Vim, SPC in Normal mode is a synonym for l, which almost nobody relies on. In our parser (keys.ts), a space at the start stage matches no list and falls through to done(null), so today it does nothing. Doom Emacs and Spacemacs use SPC as the leader in evil's normal state for the same reason.

NORMAL has an advantage over INSERT here: space never types text, so the leader works whatever the draft holds. That fixes the one awkward thing about DoomPi's rule, which only works on an empty prompt.

Edge cases
  • Mid-command. d SPC, 2 SPC or f SPC: only take the leader when engine.pending === "". Otherwise the space goes to the parser, so f SPC still finds a space.
  • Paste. The paste guard runs first, so a pasted space is text.
  • Autocomplete in INSERT. An empty draft can't have autocomplete open, so SPC needs no extra check. ctrl+space should check isShowingAutocomplete(), as Esc already does.

Registering bindings

DoomPi shares one registry through a Cordis service that every package injects. We don't have that. Pi loads each extension with moduleCache: false, so a module-level registry isn't shared either. What extensions do share is pi.events, an EventBus with emit(channel, data) and on(channel, handler). The /runs idea in IDEAS.md uses the same approach.

// Any extension (crew/index.ts). No import from vi-mode.
const crewBindings = (active: boolean) => [
  { id: "crew.list",   path: [CREW, { key: "l", label: "list", detail: "crews in this repo" }], command: { name: "crew-status" } },
  { id: "crew.resume", path: [CREW, { key: "r", label: "resume" }], command: { name: "crew-resume" } },
  ...(active ? [{ id: "crew.stop", path: [CREW, { key: "x", label: "stop", tone: "exit" }], command: { name: "crew-stop" } }] : []),
];
const announce = () => pi.events.emit("leader:contribute", { source: "crew", bindings: crewBindings(isActive()) });
pi.events.on("leader:discover", announce);  // vi-mode loaded after us
announce();                                  // vi-mode loaded before us

// vi-mode/index.ts: parse once at the boundary, as DoomPi does.
pi.events.on("leader:contribute", (data: unknown) => report(registry.register(data)));
pi.events.emit("leader:discover", {});
  • Load order doesn't matter. Each side announces on startup and answers the other's announcement.
  • Updates are re-contributions. Sending the same source again replaces that source's bindings, which handles the enter/exit swap. An empty list unregisters.
  • v1 is commands only. A command binding submits /name args through onSubmit, as DoomPi does, and needs nothing from the owning extension at run time. Named actions would need a return channel (leader:action) and a context in the handler. Add them when a binding can't be written as a slash command.
  • Pi app actions are built in. Model, session and quit bindings call this.actionHandlers.get(...) directly, which is public on CustomEditor.
Copy, don't import

DoomPi's registry is MIT licensed, about 680 lines, and has no dependencies beyond its types. Port parseContribution, insertBinding and getGroup into leaderRegistry.ts, along with the relevant parts of the 449-line registry test file, and drop the hub, telemetry and Cordis wiring.

Open questions

  1. Which-key for vi itself? The same panel could list continuations after g, after an operator (d → motions and text objects), or after i/a in operator-pending mode. It's cheap once the panel exists, and it helps with discoverability. Is it noise for someone who knows vi?
  2. Idle delay. DoomPi shows the panel immediately. Emacs which-key waits for a pause, so fast chords never draw it. With the path already in the border, should the panel wait about 300 ms?
  3. Retire the chords? Keep ctrl+shift+c/s/w as aliases, or remove them once SPC c, SPC a and SPC w exist?
  4. User remaps. Panel actions are already named (IDEAS.md: "Panel: user key maps"). Should a settings file be able to move leader bindings too, as a last contribution that always wins?
  5. Diagnostics surface. DoomPi warns through a notification. Ours: a one-off ctx.ui.notify on takeover, or only in a /leader command that dumps the tree and its conflicts?
Next step

If this holds up in discussion, promote the IDEAS.md entry to TODO.md with option A, commands only, and SPC in both modes. Port the registry and its tests first: that's the part with the most edge cases and no Pi dependency.
